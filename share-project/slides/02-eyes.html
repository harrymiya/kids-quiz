把背景说清楚，结果更容易检查

上下文会影响 Agent 能看到什么、怎么做判断。记忆和 RAG 用来补充资料。这一页看几个实用做法：Skills、状态栏和检索。

⏱ 9分钟KV Cache 3 个注意点Skills · 状态栏 · RAG

上下文：一次决策时能用到的信息

块类型例子
系统提示词静态前缀（别动）身份/权限/行为准则 = 岗位说明书
工具定义静态前缀（别动）有哪些工具、参数格式
用户消息 / 模型回复 / 工具结果动态轨迹（可追加压缩）需求 + 思考 + 工具回包
🔒 KV Cache 3 个注意点① 系统词和工具定义尽量稳定，频繁改动会影响缓存效果；② 时间戳等动态信息放在末尾，不要混进系统词，以免增加延迟和费用；③ 使用标准 API 格式，不要自己拼接 "USER:…ASSISTANT:…"，减少解析和兼容问题。

三个实用做法（可以直接参考）

📚 Skills · 按需提供知识

三层：目录（简短说明）→ SKILL.md（按需读取）→ 子文档。目录写清“什么时候用”，不用把全部内容一次塞进去。

📊 状态栏 · 记录进度

模型不一定记得已经做过什么。可以用代码维护 TODO、时间和环境摘要，放在上下文末尾，减少重复操作，也方便排查问题。

🗜 压缩 · 保持重点清楚

除了内容超长，也要注意重要信息被埋在大量记录里。可以按摘要、删噪声、归档、必要时查看全文的顺序处理。相对独立的任务也可以单独运行，主流程只接收结论。

图 · 简短需求 vs 信息比较完整的请求可以优先补充五类信息：角色 / 背景 / 约束 / 例子 / 工具。

记忆 + RAG：一句话简介（先了解概念）

概念一句话用人结论
个体记忆 vs 群体知识库前者记“你”（偏好/历史），后者记“大家”（文档/规范）。技术同源，都怕过期冲突。
存三层 / 怎么存 / 存什么放哪：会话流水 / 跨会话档案 / 任务状态。怎么存：小事便签、少量关键用结构化卡、大多混合。存啥：事件/知识/流程三类。
RAG 流程检索片段→放进上下文→生成。块大小和重叠比例可以先用经验值，再按实际数据调试。
稠密 vs 稀疏 vs 混合向量检索擅长找相近含义，关键词检索更容易命中特定词。可以先从混合检索和重排开始，再根据效果调整。
RAPTOR vs GraphRAG树（层层摘要，适合问全貌）vs 图（实体关系，适合多跳）。普通团队：自然语言存正文+结构化元数据做索引就够。
Agentic RAG / 上下文感知检索前者=检索也走 ReAct（不够再查）；后者=入库时补前缀（“该公司”→ACME 2025Q2）。都为解决“搜得到、用不上”。
更新与安全更新走 PR 流水线（提-审-合，异源互审）；检索内容=不可信输入，不能直触发高风险动作。
✅ 提示注入一句话外部内容可能混入额外指令；如果 Agent 接了执行工具，风险会相应增加。可以从三点防范：标明来源 / 做角色隔离 / 依靠结构化校验。
🎙 提示词（点击展开，9′）

开篇（1′）：“可以把 Agent 看成一个需要持续补充信息的新同事。文档、背景和例子越清楚，它越容易按要求做；只靠口头说明，结果就更需要人工检查。上下文会影响它能做什么。”

这部分的几个注意点（2′）：“简单记成三点：稳定的内容尽量保持稳定，动态信息放末尾，接口使用标准格式。这样做通常更利于缓存，也更少遇到兼容问题。”

三个做法（3′）：“Skills 像按需查的小册子，目录先放着，用到再读全文；状态栏记录 TODO、报错和环境，帮助减少重复操作；压缩不只是为了省长度，也要让重点更容易找到。任务彼此独立时，可以分开处理，主流程只接收结果。”

RAG（3′）：“记忆可以分成‘记你’和‘记大家’。检索方案可以先从混合检索和重排试起；树状结构更适合看总览，图结构更适合查关系。知识库更新要经过提交和审核，检索回来的内容也应该先当作不可信输入，不要直接触发高风险操作。”
